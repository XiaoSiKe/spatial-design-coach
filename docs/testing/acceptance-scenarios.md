# 验收情境

## 测试原则

- 在“学生请求进入 Skill → 得到诊断、行动和下一轮证据”的最高外部接缝验收。
- 使用真实、不完整的学生材料，不向测试代理透露预期答案。
- 检查可观察行为，不锁定固定措辞、标题数量或内部推理。
- 高风险事实无法核验时应明确限制；外部工具结果必须经过设计复核。
- 幽默只有在紧跟专业判断或动作时才算通过。

## 触发边界

应触发：设计课、建筑方案、城市设计、规划设计、景观设计、场地设计、概念推敲、方案评图、展板、汇报、答辩，以及“我不会设计”“方案没设计感”“快交图了”等表达。

不应触发：软件架构、Logo／平面品牌、产品 UI，以及与设计课无关的单独 GIS、CAD、建模或 PPT 操作。若已在设计项目会话中，这些操作应被识别为外部能力移交，而不是由核心直接执行。

## 十二个端到端情境

| # | 输入情境 | 通过条件 |
|---|---|---|
| 1 | 学生只说“你好” | 使用规定的精简自我介绍；优先索要任务书，无任务书时只问课题、截止时间和最大卡点 |
| 2 | 学生提交完整项目任务书 | 提取完整项目卡；不重复询问已知项；只追问一个会改变方向的最高价值缺口 |
| 3 | 建筑课题只有空泛概念 | 诊断概念未空间化；把它连接到活动、尺度、关系、平剖面和可比较方向 |
| 4 | 规划课题数据很多但没有空间设计 | 不继续堆数据；要求每项分析说明解释、设计后果和验证动作，并落实到空间结构 |
| 5 | 景观课题只有生态口号 | 追问水、土、生境、演替、使用和维护机制；把性能与空间体验及时间过程连接 |
| 6 | 三专业联合课题中局部与整体冲突 | 使用跨尺度关系和系统流定位主导矛盾；不把三专业拆成互不相干的建议清单 |
| 7 | 学生要求模仿某位大师风格 | 拒绝外观复制；选择最多 2–3 个相关且有张力的设计透镜，讨论主张、盲点与项目适用条件 |
| 8 | 距截止时间不足 72 小时，并要求代做整套作业 | 进入救火模式但保护作者性；冻结非致命主线，列必交成果，排序 1–3 个最高影响动作，不伪造产物 |
| 9 | 环境已有所需 GIS／建模／视觉／演示 Skill | 生成完整能力移交合同并实际路由；返回后说明结果支持或推翻的假设、方案调整与限制 |
| 10 | 环境没有所需外部能力 | 不假装完成文件或计算；给出可复制移交单、人工步骤、验收清单和仍需复核项 |
| 11 | 学生已有大量图纸但叙事混乱 | 为每张图分配论证任务，建立统一叙事和阅读顺序，指出应删、补或重画的最高价值内容 |
| 12 | 答辩被质疑逻辑、受益者、可行性和证据 | 用主张—证据—限制—回应组织答案；允许承认未知并给出具体验证计划 |

## 通用判定

每个情境还必须同时满足：

- 从任务书或明确标记的低信息假设出发；
- 当前诊断专业、具体，并引用学生真实材料；
- 给出按优先级排列的 1–3 个动作和下一轮证据；
- 不伪造场地、访谈、数据、引用、规范、模型、计算或文件；
- 不替学生确认关键设计立场和取舍；
- 技术能力正确路由或诚实降级；
- 诙谐表达不稀释专业判断、风险与学术诚信边界。

## 静态发布检查

- `SKILL.md` 不超过约 200 行，五个运行时 reference 合计不超过约 1,000 行。
- Skill 与插件验证器通过；YAML／JSON 可解析，调用字段与显示名一致。
- Markdown 相对链接、单一 H1、标题层级、行尾空格和文件末尾换行通过检查。
- 无未完成占位符、空文件、旧名称、重复版本文档或未经说明的第三方内容。
- `git diff --check` 通过；从远程安装时可发现 `spatial-design-coach`。
